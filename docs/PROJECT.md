# Mosaic — состояние проекта, архитектура и решения

Документ для сохранения: что такое Mosaic, как он устроен, почему сделано именно так, что проверено,
как собирать и выпускать, что дальше. Актуально на версию **0.11.0** (ноябрь 2026).
Репозиторий: https://github.com/LoopCh/mosaic · лицензия GPL-3.0-or-later.
Технические подробности (путь данных, процессы, права, зависимости, инструменты, расширение) —
в [ARCHITECTURE.md](ARCHITECTURE.md).

---

## 1. Что это

Mosaic — мультиядерный VPN/прокси-клиент. Маршрутизация, DNS, статистика и выбор узла живут в
небольшом ядре на Rust (**hub**), а Xray и sing-box — взаимозаменяемые **движки**, которые только
доставляют трафик до серверов. Одни и те же правила могут одновременно отправлять разный трафик на
узлы разных движков (например, YouTube через VLESS-Reality на Xray, игры через Hysteria2 на sing-box).

Платформы: **Windows** (основная, проверено), **Android** (проверено), **Linux** (собрано, ждёт проверки).
Интерфейс: английский и русский, приложение не привязано ни к одной стране.

### Принципы

1. Любой узел из любой подписки работает «из коробки»: клиент сам выбирает подходящее ядро.
2. Одна маршрутизация и один DNS на все ядра.
3. Переключение узла мгновенное, без разрыва TUN и перезапуска ядер.
4. Прозрачность: для каждого соединения видно правило, узел, ядро и приложение.
5. Безопасные обновления: контрольные суммы, проверка, автоматический откат.
6. Одна кодовая база логики (Rust) на все ОС; один интерфейс (HTML/JS) на десктопе и Android.

### Чем отличается от других клиентов

Hiddify, v2rayN, NekoBox, Clash Verge и др. — оболочки над одним ядром за раз: правила и DNS живут
внутри ядра, смешивать ядра в одной сессии нельзя. У Mosaic маршрутизация поверх ядер, поэтому
возможны смешение ядер, failover между ними (Smart Connect) и единый журнал соединений.

## 2. Архитектура

```
приложения ──▶ захват ──▶ hub (Rust) ──▶ движок узла (Xray / sing-box) ──▶ сервер
               (системный прокси | локальный прокси | TUN)     └──▶ direct / block
```

* **Захват**
  * *Системный прокси* — Windows (реестр + InternetSetOptionW), Linux (GNOME gsettings, KDE kioslaverc).
  * *Прокси* — только локальный SOCKS5/HTTP 127.0.0.1:7890 (или 0.0.0.0 при «доступе из сети»).
  * *TUN* — весь трафик системы (см. §4).
* **Hub** — смешанный вход SOCKS5 (CONNECT + UDP ASSOCIATE) + HTTP, роутер правил (первое совпадение
  сверху вниз, иначе «всё остальное»), диспетчер. Таблица маршрутизации заменяется атомарно
  (`Arc<RwLock<Arc<Routing>>>`), поэтому смена узла мгновенна.
* **Движки** — отдельные процессы, по одному на ядро; на каждый узел у ядра свой локальный SOCKS-вход.
  Ядро ничего не знает о правилах.
* **UI** — не участвует в передаче данных: вызывает команды контроллера и показывает снимок состояния.

### Единая модель (IR)

`Node { protocol, transport, security, engine }`:
* protocol: vless, vmess, trojan, shadowsocks, hysteria2, tuic, wireguard;
* transport: tcp, ws, grpc, httpupgrade, xhttp;
* security: none, tls{sni, alpn, fingerprint, insecure}, reality{sni, pbk, sid, fp, spx};
* engine: auto | xray | singbox.

Импорт: ссылки vless:// vmess:// trojan:// ss:// hy2:// hysteria2:// tuic:// wireguard://, base64-подписки,
WireGuard .conf, QR-код и буфер обмена (Android). Компиляторы IR → конфиг Xray / sing-box.

Матрица возможностей: Xray — VLESS/VMess/Trojan/SS (включая XHTTP); sing-box — всё, кроме XHTTP.
Auto выбирает Xray для VLESS/VMess/Trojan, sing-box для остального.

### Правила

Типы: домен, домен и поддомены, домен содержит, IP/подсеть, порт, GeoIP, Geosite, приложение
(Windows: `telegram.exe`; Linux: `telegram-desktop`; Android: имя пакета `org.telegram.messenger`).
Цели: напрямую, блок, выбранный узел, конкретный узел (на любом ядре).
Пресеты без привязки к стране: «Моя страна напрямую» (выбор страны → её домен верхнего уровня + GeoIP),
«Блок рекламы» (geosite:category-ads-all), «Сбросить» (приватные сети напрямую).
GeoIP/Geosite: собственный парсер protobuf `geoip.dat`/`geosite.dat`, загружаются только нужные коды.
Стратегия доменов: как есть / резолвить, если доменные правила не сработали (аналог IPIfNonMatch).

### DNS

* Режимы прокси: имена резолвит удалённая сторона.
* TUN: fake-IP (198.18.0.0/15); A → фиктивный адрес, по нему hub узнаёт домен; AAAA/HTTPS/SVCB → пусто
  (чтобы приложения не обходили fake-IP); прочие типы (MX, TXT, SRV…) — через туннель на «удалённый DNS»
  (по умолчанию 1.1.1.1, DNS-over-TCP через узел).
* Где резолвить имена для GeoIP/IP-правил: через VPN (приватно, по умолчанию) или локально.
* Windows: защита от утечек DNS работает по принципу «лучше не подключиться, чем течь»: если фильтры
  не ставятся или проверка после подключения (новое имя должно разрешиться в fake-IP 198.18.x.x) не
  проходит, Mosaic не подключается и объясняет причину.
* Windows: защита от утечек DNS фильтрами WFP (динамическая сессия: порт 53 разрешён только Mosaic,
  его ядрам и TUN-интерфейсу; фильтры снимаются даже при падении). Проверено dnsleaktest.

### Smart Connect

Проверка активного узла каждые 20 с, всех — раз в 3 мин. Переключение, если активный не отвечает
дважды или другой быстрее более чем на 30 % + 50 мс. Ручной выбор узла выключает режим.

### Задержка

Два числа: **круг через узел** (второй запрос по уже открытому соединению — сравнимо с пингом в
speedtest) и, мельче, **новое соединение** (первый байт ответа: TCP + TLS/REALITY-рукопожатия с узлом,
подключение узла к тестовому сайту, запрос; обычно ≈ 3 пинга). Smart Connect сравнивает второе.
Тестовый адрес: `http://www.gstatic.com/generate_204`.

## 3. Код

```
Cargo.toml                 workspace
crates/mosaic-core         вся логика (без UI)
  model.rs                 IR, настройки, состояние
  links.rs                 парсеры ссылок и подписок
  engines/{xray,singbox}   компиляторы конфигов, поиск бинарников, TUN-адаптер sing-box
  hub.rs, udp.rs           вход SOCKS5/HTTP, роутер, UDP, тест задержки
  rules.rs, geo.rs         правила, GeoIP/Geosite
  dns.rs, resolver.rs      DNS-кодек, fake-IP, резолверы, DNS через узел
  sniff.rs                 TLS SNI / HTTP Host
  tun_native.rs            собственный TUN-стек: ipstack + wintun (Windows) или fd (Android)
  procinfo.rs              владелец соединения: Windows IP Helper, Linux /proc, Android через хук
  wfp.rs                   Windows: защита от утечек DNS
  linux.rs                 Linux: системный прокси, автозапуск, копия ядер, setcap для TUN
  sys.rs                   системный прокси, автозапуск, права (по платформам)
  updates.rs               обновления ядер и приложения с GitHub (SHA-256, staging, откат)
  controller.rs            склейка: подключение, режимы, Smart Connect, фоновые задачи
  api.rs                   все команды UI одной JSON-точкой входа (для Android)
crates/mosaic-cli          консольный клиент (для разработки, в релизы не входит)
crates/mosaic-android      JNI-библиотека libmosaic.so для Android
app/src-tauri              настольное приложение (Tauri 2): окно, трей, single instance, команды
app/ui                     интерфейс (HTML/CSS/JS без сборщика), i18n EN/RU, адаптивная вёрстка
android/                   Android-проект (Kotlin): WebView + мост, VpnService, плитка, автозапуск
scripts/                   загрузка ядер: get-engines.ps1 (Windows), -android.sh, -linux.sh
.github/workflows/         windows.yml, android.yml, linux.yml, release.yml
```

Один и тот же `app/ui` работает в Tauri (`window.__TAURI__.core.invoke`) и в Android WebView
(`android.js` подменяет `invoke` мостом в Kotlin → JNI → `api::dispatch`). Различия платформ в UI:
`data-platform` на `<html>`, классы `desktop-only` / `windows-only` / `android-only`, строки `ключ@android`,
`ключ@linux`.

## 4. Платформы

### Windows (проверено)

* Установщик NSIS на пользователя (EN/RU, ядра внутри) + портативный zip; релиз по тегу.
* Режимы: системный прокси, прокси, TUN. TUN требует прав администратора.
* Два TUN-стека:
  * *адаптер sing-box* (по умолчанию) — отдельный sing-box с TUN-входом, fake-IP, отдаёт трафик в hub;
    правила по приложениям компилируются в него;
  * *native* — wintun + ipstack, fake-IP DNS, сниффинг, обходные маршруты netsh для серверов узлов,
    прямые сокеты hub привязаны к физическому интерфейсу (IP_UNICAST_IF).
* Трей, автозапуск (Run-ключ или планировщик с наивысшими правами — тогда TUN работает при входе),
  автоподключение, режим при запуске, single instance (mutex + event), доступ из локальной сети.
* Обновления ядер из приложения и проверка новых версий Mosaic (установка только по кнопке).

### Android (проверено, 0.5–0.6.1)

* Интерфейс — тот же `app/ui` в WebView; ядро — та же Rust-библиотека через JNI.
* VPN: VpnService создаёт интерфейс, его дескриптор отдаётся собственному стеку Mosaic. Mosaic
  исключён из VPN (addDisallowedApplication) — ядра и прямые соединения не зацикливаются. В режиме
  «Блокировать соединения без VPN» система всё равно пропускает само VPN-приложение.
* Ядра — официальные Android-сборки Xray/sing-box, упакованы как `libxray.so` / `libsingbox.so`
  (Android разрешает запуск только из папки нативных библиотек; `useLegacyPackaging`).
  Адреса серверов узлов резолвит Mosaic и передаёт ядрам как IP (Go на Android не может пользоваться
  системным DNS), имя сохраняется в SNI/Host.
* Режим «Прокси», уведомление с «Отключить», плитка в шторке, автоподключение (при включении телефона
  и при открытии), поддержка системной «Постоянной VPN», выбор приложений для VPN (все / кроме / только),
  правила по приложениям (владелец соединения: `ConnectivityManager.getConnectionOwnerUid`, Android 10+),
  импорт из буфера и по QR.
* Обновление ядер и проверка версий внутри приложения отключены (система не разрешает запускать
  скачанные файлы; новые версии — APK из релиза).
* Только arm64, Android 8+. Подпись — ключ из секретов репозитория (см. §5).

### Linux (0.7, собрано в CI, ждёт проверки)

* `.deb`, `.rpm`, `.AppImage` (x86_64, ubuntu-22.04 → glibc 2.35+).
* Системный прокси: GNOME-совместимые (gsettings) и KDE Plasma; иначе режим «Прокси».
* TUN: два стека, как на Windows. **Собственный** (0.8): маленький помощник `mosaic-tun-helper` (рядом с Mosaic,
  запускается из копии с `cap_net_admin`) создаёт постоянный TUN-интерфейс, владелец которого — пользователь,
  поэтому Mosaic подключается к нему без прав; помощник ставит маршруты 0/1 + 128/1 в туннель, обходные /32 для
  серверов узлов, маршруты DNS-серверов системы в туннель, DNS интерфейса в systemd-resolved (`~.`), и всё
  убирает, когда закрывается его stdin (отключение, выход или падение Mosaic). Прямые сокеты Mosaic привязаны
  к физическому интерфейсу (SO_BINDTODEVICE, без прав с Linux 5.7). Правила по приложениям — в hub через /proc,
  поэтому «Применить» всегда мгновенно.
* Второй стек — TUN: адаптер sing-box со стеком gVisor (системный стек пропускает пакеты через цепочку INPUT,
  и включённые по умолчанию ufw/firewalld их отбрасывают). Mosaic не запускается от root: при первом включении один запрос пароля
  (polkit/pkexec), который выполняет `setcap cap_net_admin,cap_net_raw,cap_net_bind_service+ep` на
  собственной копии sing-box в `~/.config/mosaic/bin`. Нативный стек на Linux пока не используется.
* Защита от петли в TUN: серверы узлов исключены из маршрутов TUN (`route_exclude_address`), ядра
  получают серверы как IP (резолв до подъёма TUN). Одного исключения по имени процесса на Linux мало:
  процесс из файла с capability становится «non-dumpable», и адаптер не видит владельца его сокетов.
  Поэтому capability стоит на отдельной копии `sing-box-tun`, а не на ядре.
* Ядра копируются из пакета в `~/.config/mosaic/bin` (исполняемые, допускают capability); обновления
  ядер работают (tar.gz).
* Правила по приложениям: в режимах прокси владелец из /proc (`/proc/net/tcp*` → inode → `/proc/*/fd`),
  в TUN — правила внутри sing-box.
* Автозапуск — `~/.config/autostart/mosaic.desktop`; single instance — сокет в `$XDG_RUNTIME_DIR`.
* Проверить на Windows-ПК можно в WSL2 (WSLg) или в виртуальной машине с Ubuntu.

## 5. Сборка и выпуск

* **CI**: `windows.yml` (тесты + портативная сборка), `android.yml` (тесты ядра на Linux, библиотека
  через cargo-ndk, APK), `linux.yml` (deb/rpm/AppImage). Артефакты — в разделе Artifacts запуска.
* **Релиз**: поднять версию везде (`crates/*/Cargo.toml`, `app/src-tauri/Cargo.toml`,
  `tauri.conf.json`, `android/app/build.gradle.kts` — versionName и versionCode), затем
  `git tag vX.Y.Z && git push origin main vX.Y.Z`. `release.yml` проверяет, что тег совпадает с версией,
  собирает Windows (setup.exe, zip, SHA256SUMS), Android (APK, SHA256SUMS-android), Linux
  (deb/rpm/AppImage, SHA256SUMS-linux) и публикует релиз. Если тег уже был — `git tag -f` +
  `git push -f origin vX.Y.Z`, старый релиз удалить на GitHub.
* **Подпись Android**: секреты `ANDROID_KEYSTORE_B64`, `ANDROID_KEYSTORE_PASSWORD`,
  `ANDROID_KEY_ALIAS`, `ANDROID_KEY_PASSWORD`. Ключ создаётся `keytool` (есть в Java Android
  Studio / RustRover), base64 в PowerShell: `[Convert]::ToBase64String([IO.File]::ReadAllBytes(...))`.
  Ключ хранить в надёжном месте: без него обновлять установленные копии нельзя.
* **Локально**: Windows — `scripts\get-engines.ps1`, `cargo run --release -p mosaic`; установщик —
  `npx @tauri-apps/cli@2 build` в `app/src-tauri`. Android и Linux — команды в README.

### Обновления (как устроены)

* Ядра: последний релиз XTLS/Xray-core или SagerNet/sing-box → архив для своей ОС → SHA-256 (поле
  `digest` GitHub, `.dgst` у Xray или SHA256SUMS; без суммы установка отклоняется) → распаковка во
  временную папку → `version` → отключение → замена (старые файлы в резерв) → проверка с узлами
  пользователя / переподключение → при ошибке автоматический откат. Обновлённые ядра лежат в папке
  данных и имеют приоритет над встроенными; «Вернуть встроенные версии» видна, только если они есть.
* Приложение (Windows): раз в день проверка релизов LoopCh/mosaic (можно отключить), баннер,
  загрузка `*-setup.exe` с проверкой SHA-256, запуск установщика по кнопке. Linux: баннер открывает
  страницу релиза. Android: отключено.

Ключевые решения и причины:

* **Ядра — отдельные процессы**, а не встроенные библиотеки: проще обновлять, падение ядра не роняет
  приложение, лицензии ядер (GPL/MPL) не смешиваются с кодом на десктопе.
* **Свой hub поверх ядер** вместо «конфиг ядру целиком»: смешение ядер, единые правила/DNS/статистика,
  мгновенная смена узла.
* **Петля DNS в адаптере sing-box** (системный резолвер возвращал fake-IP) решена отдельным
  SOCKS-входом для прямых соединений hub и DNS-правилами для доменов серверов.
* **Android: один UI для всех платформ** (WebView) вместо Compose — быстрее и одинаково везде;
  нативный Compose возможен позже.
* **Linux: capability вместо root** — GUI не должен работать от root; capability ставится на
  собственную копию sing-box, поэтому годится и для AppImage.

## 7. Ограничения и известные вопросы

* Tailscale с «Use Tailscale DNS settings» (MagicDNS) и корпоративные VPN ставят в Windows правило NRPT
  «все имена → свой DNS», которое сильнее DNS любого адаптера. С включённой защитой от утечек Mosaic в
  этом случае не подключается и называет причину; решение — выключить DNS Tailscale на время TUN.
* Программы обхода DPI, переписывающие исходящие пакеты (zapret, GoodbyeDPI), могут ломать соединения
  с серверами узлов — их нужно исключать или выключать.
* Linux: системный прокси только GNOME/KDE; только x86_64; защита от утечек DNS опирается на systemd-resolved
  и маршруты DNS-серверов (проверки DNS после подключения, как на Windows, пока нет).
* Android: только arm64; нет armv7/x86_64; правила по приложениям — Android 10+ и только в VPN.
* Сохранение настроек на Android при подключении переподключает соединение (интерфейс принадлежит службе).
* Подпись релизов приложения (Tauri updater) не сделана — целостность обеспечивает SHA-256 из релиза.
* macOS и iOS не начаты.

## 8. Дальше (план)

1. Проверка Linux-сборки (WSL2 или виртуальная машина), исправления по результатам.
2. macOS (Tauri собирается; TUN через адаптер sing-box от root/helper или NetworkExtension; нужна

6. Android: armv7/x86_64, обновление APK из приложения (с REQUEST_INSTALL_PACKAGES), нативный UI.

## 9. Распространение и заработок (кратко)

GPL-3.0 разрешает продавать и распространять за деньги, но исходники остаются открытыми, и мобильные
сборки с GPL-ядрами тоже GPL. Реальные модели: донаты (GitHub Sponsors, Boosty/Patreon), брендированные
сборки и поддержка для VPN-провайдеров (самый доходный вариант), партнёрские программы провайдеров
(с честной пометкой), платные сборки в магазинах при открытом коде, платные сервисы вокруг клиента
(синхронизация, мониторинг узлов). Двойное лицензирование возможно только для собственного кода и
при CLA от всех участников. В ряде стран распространение и реклама VPN регулируются — перед
коммерческим запуском нужна консультация юриста.
